# Contributing

Thank you for helping improve Obsidian Knowledge Vault for macOS and Windows.

## Before opening a pull request

1. Do not add real notes, vault exports, logs, screenshots, account data, or credentials.
2. Keep deployment behaviour explicit: never overwrite a user's existing notes or silently send material to an external model.
3. Run the privacy gate:

   ```sh
   python3 tools/scan_privacy.py --root . --scope public
   ```

4. Validate the published package rather than only source files:

   ```sh
   PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -v
   PYTHONDONTWRITEBYTECODE=1 python3 scripts/build_release.py
   ```

5. Explain the user-facing impact and any privacy or compatibility change in the pull request.

## Pull-request rules

Automated privacy and release-package checks must pass before a pull request
merges. Changes merge automatically after those checks pass; no manual approval
is required by default.

## Repository framework status

This repository follows the personal GitHub project standard
(`~/code/agent-norms/public-repo/project-standard.md`). Reviewed 2026-10-14; every deviation is
listed below with a reason.

**In place**: `README.md` + `README.zh-CN.md` (mutually linked), `LICENSE` (MIT),
`CONTRIBUTING.md`, `SECURITY.md`, `SUPPORT.md`, `CHANGELOG.md` (generated by Release Please),
`docs/`, `scripts/`, `tests/`, `tools/scan_privacy.py`, `.github/pull_request_template.md`, and
the workflows `test.yml` (CI), `codeql.yml`, `privacy-gate.yml`, `release-please.yml`,
`auto-merge-own.yml`.

**Known deviations** (2026-10-14):

- **CI file is `test.yml`, not `ci.yml`**: same job — unit tests plus the release-package build,
  on push and on pull requests.
- **No npm release chain** (`publish-npm.yml`, `verify-npm-release.yml`, OIDC trusted publishing):
  the release artifact is a package built by `scripts/build_release.py` and attached to the GitHub
  release, not an npm package.
- **No `release-please-config.json` / `.release-please-manifest.json`**: inline
  `release-type: simple` already emits `vX.Y.Z` tags without a component prefix. Moving to a
  manifest config requires seeding the manifest with the current version first; done wrong it makes
  Release Please recompute a major version from the entire history. Deliberately kept as is.
- **No `lib/` build artifact**: build output is produced per release and attached to the GitHub
  release instead of being committed to the repository.
- `deploy.py` moved out of the repository root on 2026-10-14: it is now `scripts/deploy.py`.
  `scripts/build_release.py` copies it to the top level of the published package, so the documented
  package command stays `python3 deploy.py` and only the repository-checkout command changes, to
  `python3 scripts/deploy.py`. The move is safe for people who already installed a package: the
  shipped installer templates (`payloads/macos/脚本/*.sh.tpl`) mention `deploy.py` only in a
  provenance comment and never call it, the rendered scripts in the installed project directory read
  `$PROJECT/程序` and `$PROJECT/脚本` instead, and `deploy.py` itself is not part of the installed
  payload (`macos_install` / `windows_install` copy only the payload directories).
- The release security checklist moved out of the repository root on 2026-10-14: it is now
  `docs/zh-CN/RELEASE-SECURITY-CHECKLIST.md`.
- **No human approval for the owner's pull requests** (corrected 2026-10-14): an earlier version
  of this record said commits go straight to `main`. That is no longer true — `main` is protected
  (required checks `analyze-python`, `release-contract (macos-latest)`,
  `release-contract (windows-latest)` and `scan`; `enforce_admins` on; force pushes and deletions
  blocked), so a direct push to `main` is rejected and every change lands through a pull request.
  Because `required_approving_review_count` is 0 and `auto-merge-own.yml` turns on auto-merge for
  owner pull requests, the owner's own PRs still merge without a manual click once CI is green.
  Other people's pull requests stay manual.

Any deviation from the standard belongs in this section, with a reason and a date.
